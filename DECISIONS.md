# Decisions

Record architecture and product decisions here.

| Date | Decision | Why | Alternatives Rejected |
| --- | --- | --- | --- |
| 2026-08-26 | Keep support ticket writes agent-owned under forced RLS; dashboard access remains service-role-only. | Mobile agents need direct creation/read access without being able to update status, impersonate another agent, or read another agent's messages. | Public/anonymous access; client-side status updates; broad authenticated policies. |
| 2026-08-26 | Treat the live Supabase migration ledger as authoritative and mirror its exact versions, names, and stored SQL locally. | Historical placeholders and application-time version drift prevented reliable comparison and continuation. | Rewriting live migration history; retaining generic placeholder files. |
| 2026-08-26 | Bootstrap new Supabase projects from a dated schema-only cutover baseline, then mark only the frozen pre-cutover migration versions as applied. | The production schema predates the first recorded migration, while linked `pg_dump` is unavailable to the current account. A catalog-derived snapshot restores deterministic empty-project reproduction without rewriting production history. | Replaying migrations that assume pre-existing tables; rewriting the live ledger; marking all future migrations as applied. |
| 2026-08-26 | Track demonstration records with both `is_demo` and a foreign-keyed `demo_batch`, and remove them only through a service-role cleanup RPC exposed to super admins. | Demo workflows must be realistic across related tables while remaining visually distinct, auditable, and removable without broad or heuristic deletes. | Unmarked seed rows; naming conventions; ad-hoc SQL deletion; separate demo database. |
| 2026-08-26 | Use the shared database as the integration contract for admin campaigns/content/support, developer inventory, and the mobile client. | Database-backed operations keep all three surfaces synchronized and eliminate dashboard-only placeholder state. | Client-only mock state; duplicated dashboard/mobile APIs for resources already protected by RLS. |
| 2026-08-26 | Deliver phone alerts through Expo Push Service from PostgreSQL `pg_net`, with authenticated token registration, 100-token batching, cron response processing, and bounded retries. | It extends the existing database campaign scheduler without adding another always-on service or exposing provider credentials to the app. | Mobile-originated sends; a dashboard-only synchronous request; direct APNs/FCM integrations; untracked fire-and-forget requests. |
