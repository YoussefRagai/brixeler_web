# Decisions

Record architecture and product decisions here.

| Date | Decision | Why | Alternatives Rejected |
| --- | --- | --- | --- |
| 2026-08-26 | Keep support ticket writes agent-owned under forced RLS; dashboard access remains service-role-only. | Mobile agents need direct creation/read access without being able to update status, impersonate another agent, or read another agent's messages. | Public/anonymous access; client-side status updates; broad authenticated policies. |
| 2026-08-26 | Treat the live Supabase migration ledger as authoritative and mirror its exact versions, names, and stored SQL locally. | Historical placeholders and application-time version drift prevented reliable comparison and continuation. | Rewriting live migration history; retaining generic placeholder files. |
| 2026-08-26 | Bootstrap new Supabase projects from a dated schema-only cutover baseline, then mark only the frozen pre-cutover migration versions as applied. | The production schema predates the first recorded migration, while linked `pg_dump` is unavailable to the current account. A catalog-derived snapshot restores deterministic empty-project reproduction without rewriting production history. | Replaying migrations that assume pre-existing tables; rewriting the live ledger; marking all future migrations as applied. |
| 2026-08-26 | Track demonstration records with both `is_demo` and a foreign-keyed `demo_batch`, and remove them only through a service-role cleanup RPC exposed to super admins. | Demo workflows must be realistic across related tables while remaining visually distinct, auditable, and removable without broad or heuristic deletes. | Unmarked seed rows; naming conventions; ad-hoc SQL deletion; separate demo database. |
| 2026-08-26 | Use the shared database as the integration contract for admin campaigns/content/support, developer inventory, and the mobile client. | Database-backed operations keep all three surfaces synchronized and eliminate dashboard-only placeholder state. | Client-only mock state; duplicated dashboard/mobile APIs for resources already protected by RLS. |
| 2026-08-26 | Deliver phone alerts through Expo Push Service from PostgreSQL `pg_net`, with authenticated token registration, 100-token batching, cron response processing, and bounded retries. | It extends the existing database campaign scheduler without adding another always-on service or exposing provider credentials to the app. | Mobile-originated sends; a dashboard-only synchronous request; direct APNs/FCM integrations; untracked fire-and-forget requests. |
| 2026-08-26 | Treat account suspension and developer content approval as database-enforced states, with Auth bans and dashboard UI as secondary controls. | Existing JWTs and multiple clients make UI-only enforcement insufficient; the shared database must fail closed while preserving an own-profile status read. | Navigation-only blocking; Auth ban alone; dashboard-only moderation labels. |
| 2026-08-26 | Count Expo delivery only after receipt processing, not push-ticket acceptance. | Expo ticket acceptance means queued by the provider, not delivered to the device. | Treating HTTP 200/ticket IDs as delivery; untracked fire-and-forget pushes. |
| 2026-08-26 | Keep dashboard navigation grouped in the shared shells and make project setup a client-side five-step view over the existing multipart server action. | Grouping reduces the flat admin menu without changing role filtering; client-only step state preserves every existing field and server/database contract while reducing cognitive load. | New persistence/API for drafts; separate route per step; role-blind navigation. |
| 2026-08-26 | Use a shared desktop command-center rhythm in both dashboard shells, with compact chrome, restrained card treatment, and dense list/stat bands above 1024px. | The existing mobile-first spacing made desktop feel oversized and scattered; shell-level styling improves every admin/developer route while breakpoint scoping preserves the accepted mobile view. | Page-by-page desktop overrides; larger hero copy; adding a new visual dependency. |
| 2026-08-27 | Treat `listed_by_agent_id` as resale lifecycle ownership: agent-origin rows are developer-visible but read-only, while developer-origin rows have a null agent owner and remain developer-managed. | Both resale sources belong under the same project, but project ownership must not let a developer edit, delete, hide, or renew an agent's mobile listing. | Duplicating resale tables; granting project owners full listing control; hiding agent submissions from developers. |
| 2026-08-27 | Ship compatibility-safe global response headers now, defer CSP until a nonce/origin strategy is tested, and scope browser drafts to the signed-in developer while excluding file inputs. | A static strict CSP would currently break Next.js inline RSC/hydration or approved external media, and global draft keys could expose one developer's unfinished form to another account on a shared browser. | `unsafe-inline` CSP; an untested strict static CSP; global draft keys; persisting browser file inputs or creating a new server-side draft service. |
| 2026-08-27 | Make cross-surface support/contact writes atomic in SECURITY DEFINER RPCs with narrow grants, and compensate storage objects when database writes fail. | User-visible partial success creates orphaned files, missing messages, or missing notifications that the dashboards and app cannot reconcile reliably. | Best-effort multi-step client/server writes; hiding partial failures; periodic orphan cleanup as the primary mechanism. |
| 2026-08-27 | Generate Supabase types only from an isolated database rebuilt from repository migrations, and fail the check on drift. | Live-schema generation can silently bless migration drift and does not prove a clean database can be reproduced. | Hand-maintained database types; generating from production; allowing CI to update generated files automatically. |
| 2026-08-29 | Use one shared Growth contract for reusable audiences, lifecycle scheduling, independent approval, versions, evaluation, and mobile visibility. | Non-technical admins need predictable builders while the database remains the authority across admin, mobile, notifications, and fulfillment. | Per-page filter JSON; browser-only drafts; UI-only approval; separate mobile campaign logic. |
| 2026-08-29 | Keep demo Growth resources explicitly flagged, batched, draft, and inactive until deliberately approved. | Demonstration data must exercise real workflows without becoming customer-visible and must be removable exactly before launch. | Name-based demo detection; active fake campaigns; a separate mock-only UI. |
| 2026-08-29 | Treat the cutover manifest and pre-tracking extension prerequisites as executable bootstrap contracts. | A malformed version and missing `pg_cron` reproduced only on a genuinely clean database; validating both prevents migration history from appearing healthy while clean-project reproduction is broken. | Testing only the newest migration; relying on production-only extension state; accepting arbitrary manifest text. |
