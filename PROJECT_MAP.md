## Data Flow

- Browsers authenticate to Next.js; signed local cookies carry admin/developer session identifiers.
- Server routes and actions use the Supabase service-role client for privileged reads and writes.
- Mobile calls `/api/mobile/phone-verification/*` and `/api/mobile/developer-contact-requests` with a Supabase bearer token.
- Shared Supabase tables, storage, RPCs, Auth users, and edge functions connect this service to `brixeler-mobile`.
- `support_tickets` and `support_ticket_messages` are shared support resources: authenticated agents can read/create only their own records through RLS, dashboard mutations use the service role, and message inserts synchronize ticket activity fields.
- `demo_data_batches` groups all disposable demo records; `cleanup_demo_batch` is service-role-only and the super-admin Settings screen is the intended removal surface.
- `notification_campaigns` is dispatched into mobile-readable `notifications` rows by a pg_cron worker; `dashboard_content`, `support_macros`, `admin_tasks`, `admin_agent_notes`, and `admin_export_jobs` persist dashboard operations.
- `growth_audiences` is the reusable targeting source for gifts, rewards, campaigns, and managed content; database lifecycle, approval, date, and audience checks determine evaluation and mobile visibility.
- `device_push_tokens` stores authenticated Expo device tokens; `push_delivery_batches` tracks Expo submission responses and bounded retries, with pg_cron processing every minute.
- `developer_projects.approval_status` gates project/unit visibility in mobile; `/properties` is the admin moderation queue and developer edits automatically return content to review.
- `developer_notifications` is the developer lead inbox; contact status changes notify the requesting agent through `notifications`.
- Resales linked to a developer project are separated by origin: agent-submitted rows are visible but read-only, while rows with no `listed_by_agent_id` remain developer-managed inventory.
- Expo ticket IDs are mapped back to device tokens and receipt processing, not ticket acceptance, determines delivered/partial/failed state.
- Railway is intended to host this service at the admin/developer custom domains.
